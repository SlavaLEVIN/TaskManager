# Руководство системного программиста

## 1. Размещение

На сервере работает PostgreSQL. На рабочих станциях — одна программа TaskManager с прямым TCP/IP-подключением к БД. Приложение не требует Интернета, отдельного HTTP-сервера, Python на клиенте после упаковки или при использовании переносимого комплекта.

Для учебного запуска сервер и клиент можно разместить на одном ПК. Для LAN серверу нужен постоянный IP. Устанавливать PostgreSQL на каждый клиент не нужно. Минимум по требованиям: клиент 2 ядра, 4 ГБ RAM, 1 ГБ диска; сервер 2 ядра, 4 ГБ RAM, 2 ГБ без копий. Замеры на целевом минимальном ПК ещё не выполнены.

## 2. Установка сервера и мастер настройки

Используйте официальный [установщик PostgreSQL для Windows](https://www.postgresql.org/download/windows/). Версия локальной проверки — 18.0. В отдельную папку `Installers` поставки загружен официальный установщик **18.6-4 x64**; его выполнение на Windows и совместимость именно этой сборки ещё не проверены. Это та же основная версия 18, но результат тестирования 18.0 не выдаётся за проверку 18.6.

Установите Server и Command Line Tools. pgAdmin полезен для обслуживания. Stack Builder программе не нужен. Задайте пароль системного пользователя PostgreSQL `postgres` и запомните порт.

Распакуйте приложение и выполните `SETUP_DATABASE.cmd`. Мастер последовательно запрашивает адрес/порт, реквизиты служебного администратора PostgreSQL, имя новой базы и новой технической роли, пароль этой роли, логин/пароль первого администратора приложения. После подтверждения `CREATE` он:

1. Отказывается менять уже существующую базу или роль.
2. Создаёт отдельную роль без superuser/createdb/createrole и новую БД UTF-8.
3. Устанавливает timezone БД Europe/Moscow.
4. Создаёт схему и категории; сохраняет только bcrypt-хеш пароля первого прикладного администратора.
5. Выдаёт технической роли минимальные права клиента и сохраняет клиентский INI.

Создание PostgreSQL-роли и самой БД выполняется вне транзакции схемы: `CREATE DATABASE` требует этого. При прерывании мастера могут остаться созданные объекты. Автоматического удаления нет. Проверьте их в pgAdmin; для новой попытки используйте другие имена либо завершите настройку вручную. Не удаляйте БД с рабочими данными.

В тестах мастер выполнен с отдельным сервером. Проверены вход через созданного прикладного администратора, отсутствие superuser у технической роли и запрет CREATE TABLE штатному клиенту.

## 3. Ручная установка

Ниже команды `psql`, выполняемые служебным администратором. Пароль вводится интерактивно; не храните его в SQL-файле.

```sql
CREATE ROLE task_client LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE;
\password task_client
CREATE DATABASE task_manager ENCODING 'UTF8' TEMPLATE template0;
ALTER DATABASE task_manager SET timezone TO 'Europe/Moscow';
\connect task_manager
\i database/create_schema.sql
\i database/seed_categories.sql
REVOKE ALL ON SCHEMA public FROM PUBLIC;
GRANT USAGE ON SCHEMA public TO task_client;
GRANT SELECT, INSERT, UPDATE, DELETE ON users, tasks TO task_client;
GRANT SELECT ON categories TO task_client;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO task_client;
REVOKE ALL ON DATABASE task_manager FROM PUBLIC;
GRANT CONNECT ON DATABASE task_manager TO task_client;
SELECT lower('ИВАН') = 'иван' AS cyrillic_case_check;
```

Последняя проверка должна вернуть `true`; проверьте локаль PostgreSQL, если это не так. Тестовая БД использовала `en_US.UTF-8`, которая корректно обрабатывает кириллицу. Сравнение `lower` выполняется БД, а не Python. При необходимости новую БД можно создать с ICU-локалью `ru-RU`; менять колляцию существующей рабочей БД без миграции не следует.

Скопируйте `config/database.example.ini` в файл конфигурации своей машины, укажите техническую роль и её пароль. Для первого прикладного администратора:

```powershell
.\runtime\python.exe -X utf8 scripts\init_admin.py --config C:\TaskManager\client.ini
```

Этот скрипт отказывает, если ADMIN уже существует. Следующие прикладные пользователи создаются через приложение. Для демонстрации вместо `init_admin.py` вызовите `seed_demo.py` на пустой тестовой БД с конфигурацией владельца схемы; рабочую систему демонстрационными паролями не наполняйте.

## 4. LAN

В `postgresql.conf` задайте нужные адреса прослушивания, например:

```ini
listen_addresses = 'localhost,192.168.1.10'
port = 5432
password_encryption = 'scram-sha-256'
```

В `pg_hba.conf` добавьте только требуемую подсеть/клиенты и базу/роль:

```text
host task_manager task_client 192.168.1.0/24 scram-sha-256
```

Это пример; замените IP и подсеть реальными. Не используйте `trust` и не открывайте PostgreSQL в Интернет. В Windows Firewall разрешите входящий порт 5432 только для нужного частного профиля и адресов клиентов. Изменение `listen_addresses` требует перезапуска PostgreSQL, `pg_hba.conf` — перечитывания конфигурации.

Для недоверенной сети настройте TLS на PostgreSQL и `sslmode=verify-full` с доверенным CA; значение `prefer` по умолчанию предназначено для согласованной доверенной LAN и само по себе не гарантирует шифрование. CA для verify-full на Windows ищется libpq в стандартном `%APPDATA%\postgresql\root.crt`. [Документация libpq SSL](https://www.postgresql.org/docs/18/libpq-ssl.html).

На каждом клиенте задайте одни технические параметры БД через окно входа; затем входите под отдельным **прикладным** логином. Конфигурация содержит пароль общей технической роли; ограничьте доступ к ней своей Windows-учётной записью. Приложение не является защитой от пользователя, произвольно подключающегося к БД с этим паролем.

## 5. Конфигурация и журнал

Порядок поиска INI: путь `TASK_MANAGER_CONFIG`; затем для EXE — `database.ini` рядом с EXE; иначе `%LOCALAPPDATA%\TaskManager\database.ini`. Переносимая папка runtime не означает переносимость пароля: INI по умолчанию остаётся в профиле текущего Windows-пользователя.

Поля INI: `host`, `port`, `dbname`, `user`, `password`, `connect_timeout` (2–15 с), `statement_timeout` (1000–30000 мс), `sslmode`. Используйте один адрес сервера, а не список нескольких резервных адресов. Значение `password` читается без интерполяции `%`.

Журнал: `%LOCALAPPDATA%\TaskManager\logs\application.log`, ротация до 3 копий по 1 МБ. Записываются этап и SQLSTATE; пароль, хеш, SQL и DSN с секретами не записываются. Для исключений приложения сохраняются тип и позиции вызовов без значений данных.

Тайм-аут соединения по умолчанию 5 с, запроса 10 с, блокировки 5 с; keepalive ограничивает ожидание пропавшего соединения. Кнопка «Повторить подключение» создаёт новое соединение и проверяет таблицы. Если commit дал неизвестный результат, не повторяйте запись вслепую: сначала перечитайте данные.

## 6. Резервное копирование

В PowerShell на сервере, используя служебного администратора. Команды запрашивают пароль; `%PGPASSWORD%` в файлы не записывайте.

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\pg_dump.exe' -h 127.0.0.1 -U postgres -W -d task_manager -Fc -f 'D:\Backups\task_manager.backup'
```

Копия содержит хеши паролей и рабочие данные; храните её с ограничением доступа. Для проверки восстановления создайте **новую отдельную** БД:

```powershell
& 'C:\Program Files\PostgreSQL\18\bin\createdb.exe' -h 127.0.0.1 -U postgres -W task_manager_restore_test
& 'C:\Program Files\PostgreSQL\18\bin\pg_restore.exe' -h 127.0.0.1 -U postgres -W -d task_manager_restore_test --no-owner --no-privileges --exit-on-error 'D:\Backups\task_manager.backup'
```

Проверьте числа и содержимое users/categories/tasks, вход тестовой копии, назначения и отсутствие нарушенных связей:

```sql
SELECT count(*) FROM users;
SELECT count(*) FROM categories;
SELECT count(*) FROM tasks;
SELECT count(*) FROM tasks t
LEFT JOIN users u ON u.id=t.assignee_id
LEFT JOIN categories c ON c.id=t.category_id
WHERE u.id IS NULL OR c.id IS NULL;
```

Последний результат должен быть 0. После восстановления с `--no-privileges` отдельно выдайте права тестовой технической роли и timezone новой БД. Не перенаправляйте рабочие клиенты на тестовую копию. В комплекте нет автоматического восстановления поверх рабочей БД.

## 7. Обновление

Для EXE: завершите клиент, сохраните INI, замените EXE, запустите и проверьте подключение. Для переносимого комплекта замените папку приложения новой версией, сохранив пользовательскую конфигурацию и необходимые экспорты.

Обновление клиента не меняет схему БД. При будущей миграции сначала сделайте резервную копию и проверьте восстановление, остановите клиентов, выполните конкретный SQL из `database/migrations`, затем проверьте данные и обновите клиент. В версии 1.0 новых миграций после начальной схемы нет. Повторять `create_schema.sql` на рабочей базе для обновления нельзя.

## 8. Подготовка одного EXE

На Windows с Python 3.13 x64 выполните `BUILD_WINDOWS.cmd`. Сценарий ставит зависимости в `.venv`, запускает модульные тесты, собирает onefile GUI-приложение PyInstaller из `packaging/task_manager.spec` и включает справку/иконку. Результат — `dist/TaskManager.exe`.

Есть вручную запускаемый workflow `.github/workflows/windows.yml`. Он не был отправлен в репозиторий или выполнен; исходники никуда не опубликованы. Если использовать workflow, располагайте проект в корне своего репозитория. Сборка не заменяет функциональное испытание EXE в Windows с LAN и отключённым Интернетом.
