# Модель постоянных данных

| Таблица | Поля | Основные ограничения |
|---|---|---|
| users | id, login, password_hash, role | PK identity; непустой нормализованный по краям login; UNIQUE lower(login); формат bcrypt; CHECK USER/ADMIN |
| categories | id, name | PK identity; UNIQUE и непустое name |
| tasks | id, title, description, assignee_id, category_id, due_date, priority, status | PK identity; непустое title; FK RESTRICT; NOT NULL; CHECK приоритета/статуса; DEFAULT NEW |

Связи: User 1 — 0..* Task; Category 1 — 0..* Task. У задачи ровно один исполнитель и одна категория. Отдельных таблиц ролей, приоритетов, статусов, сотрудников, отчётов и истории нет.

Индексы `tasks_assignee_idx`, `tasks_due_date_idx`, `tasks_category_idx` поддерживают основные отборы. Для 1000 задач полный просмотр текстов достаточен. Дополнительный поисковый движок не нужен. Дальнейшая индексация определяется EXPLAIN и реальными измерениями, а не вводится заранее.

Права штатного технического клиента: CONNECT к БД, USAGE схемы, SELECT/INSERT/UPDATE/DELETE для users и tasks, SELECT/INSERT/UPDATE для categories, USAGE/SELECT последовательностей. Нет superuser, CREATE DATABASE, CREATE ROLE, CREATE в схеме, DELETE категорий. Владелец схемы — обслуживающий администратор PostgreSQL.

Сервис проверяет переходы статусов; БД проверяет допустимые значения и ссылочную целостность. Прямое SQL-подключение может обойти клиентское правило переходов и прикладные роли. Это документированная граница заданной архитектуры.

`create_schema.sql` предназначен для новой пустой базы; повторное выполнение на существующей базе прекращается ошибкой, ничего не пересоздаётся автоматически. `seed_categories.sql` заполняет справочник идемпотентно. Демонстрационные задачи добавляются отдельными скриптами, не при старте клиента.

Запросы значений параметризованы. Имена полей сортировки берутся только из `SORT_FIELDS`, направления — из логического параметра. Текущая дата берётся из PostgreSQL в той же логической операции, что чтение задач.
