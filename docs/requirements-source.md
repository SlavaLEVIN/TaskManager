# Master Prompt для разработки программы Менеджер задач

Этот промпт предназначен для передачи агенту программирования. Разработай приложение по приведённым требованиям, сохраняя согласованность кода, базы данных, интерфейса, тестов и документации.

Основа: актуальное ТЗ «ТЗ_ИУ6-54Б_Лёвин В.А..docx» и решения по курсовой работе, принятые при обсуждении схем. Пример промпта для экспертной системы используется только как образец организации документа.

## 1. Задача и результат

Разработать полноценное настольное приложение **«Менеджер задач»** для курсовой работы по дисциплине «Технология разработки программных систем».

Приложение обеспечивает централизованное управление задачами сотрудников организации и контроль их выполнения в локальной вычислительной сети без доступа к Интернету.

Основные действия: авторизация, просмотр задач, поиск, фильтрация, сортировка, изменение статусов, управление пользователями и задачами, назначение ответственного исполнителя, формирование текстовых отчётов и экспорт списков в CSV.

Результат работы: исходный код, SQL-сценарии, демонстрационные данные, работающие тесты, инструкции по установке и сборке, а также материалы для РПЗ. Основные сценарии должны работать с настоящей PostgreSQL от ввода в интерфейсе до сохранения и повторного чтения данных.

Курсовой проект должен быть понятен студенту третьего курса. Выбирай простые обоснованные решения, объясняй назначение слоёв и основных классов, не создавай лишние абстракции.

## 3. Стек и развёртывание

Использовать:

- Python — язык реализации;
- PySide6 и Qt Widgets — настольный интерфейс;
- PostgreSQL — хранение постоянных данных;
- psycopg2 — прямое подключение клиента к PostgreSQL;
- bcrypt — хеширование и проверка паролей;
- PyInstaller — сборка клиентского приложения в один `.exe`;
- pytest — инструмент разработчика для автоматических тестов.

Целевые ОС клиентов: Windows 10 и Windows 11, 64-разрядные версии.

Развёртывание:

```text
Рабочая станция пользователя     Рабочая станция администратора
      Клиент PySide6                   Клиент PySide6
              \                         /
               TCP/IP в локальной сети
                          |
             Выделенный компьютер с PostgreSQL
                          |
                  Общая база task_manager
```

На серверном компьютере отдельно устанавливается PostgreSQL. На клиенте после развёртывания не требуется установленный Python. Python и библиотеки приложения включаются в `.exe`.

Клиент подключается к PostgreSQL через psycopg2. Отдельный HTTP-сервер и REST API для этой архитектуры не предусматриваются.

В эксплуатации отсутствуют обращения к облачным сервисам, внешним API, CDN и сетевым ресурсам справки. Установка среды разработчика может требовать предварительной загрузки зависимостей; это не должно создавать зависимость работающей программы от Интернета.

ТЗ задаёт минимальную конфигурацию клиента: процессор уровня Intel Core i3 или эквивалент, 2 ядра, 4 ГБ ОЗУ и 1 ГБ свободного места. Минимальная конфигурация сервера: двухъядерный процессор, 4 ГБ ОЗУ, 2 ГБ свободного места без учёта резервных копий.

Зафиксируй реально проверенные совместимые версии Python, PostgreSQL и библиотек в документации и файлах зависимостей. Не меняй стек на C#, WPF, Prolog, PyQt5, SQLite или ORM.

## 4. Роли и права

Предусмотрены две прикладные роли:

- **Пользователь** — ответственный исполнитель назначенных ему задач;
- **Администратор** — управляет учётными записями и задачами.

Системный администратор, который устанавливает PostgreSQL и выполняет резервное копирование, является обслуживающим персоналом, а не третьей ролью интерфейса.

| Действие | Пользователь | Администратор |
|---|---|---|
| Вход, выход из учётной записи, справка | Да | Да |
| Просмотр задач и сведений о них | Только свои назначенные | Все задачи и задачи выбранного пользователя |
| Поиск, фильтрация, сортировка | Только свои назначенные | Все доступные ему задачи |
| Изменение статуса | Только своей задачи, по правилам переходов | В рамках управления задачами, по тем же правилам |
| Создание, редактирование, удаление задач | Нет | Да |
| Назначение и смена ответственного | Нет | Да |
| Список, добавление, редактирование логина/роли, удаление пользователей | Нет | Да |
| Сброс пароля пользователя | Нет | Да |
| Текстовый отчёт | По одной или нескольким своим задачам | По одной или нескольким выбранным задачам |
| Экспорт задач и пользователей в CSV | Нет | Да |
| Изменение справочника категорий через GUI | Нет | Нет |

Проверяй полномочия в сервисном слое при каждом защищённом действии. Скрытие кнопки не заменяет проверку доступа.

Не доверяй переданному из виджета идентификатору пользователя или задачи. Пользователь не должен читать, изменять или включать в отчёт чужую задачу через прямой вызов сервиса с чужим ID.

При очистке поиска, сбросе фильтров и обновлении списка ограничение по текущему пользователю сохраняется.

Изменение роли действующей учётной записи должно учитываться при следующем защищённом действии. Сервис получает актуальную роль по ID сессии из БД и не полагается только на роль, сохранённую при входе. После обнаружения изменения роли интерфейс обновляет доступные действия и очищает данные, которые больше недоступны.

## 5. Предметная модель

### User

Поля:

- `id: int` — идентификатор учётной записи;
- `login: str` — уникальный логин;
- `password_hash: str` — bcrypt-хеш, только для внутренней обработки;
- `role: Role` — `USER` или `ADMIN`.

Метод: `is_admin() -> bool`.

Логин, пароль при вводе и роль обязательны. Пустой логин и пароль недопустимы. Внешние пробелы логина можно удалять по принятому правилу; пароль нельзя незаметно изменять или обрезать.

`User` является учётной записью исполнителя. Отдельная сущность сотрудника с ФИО, должностью, компетенциями или загрузкой не требуется.

### Category

Поля:

- `id: int`;
- `name: str`.

Категории хранятся в PostgreSQL и выбираются в форме задачи из справочника.

Справочник заполняется при первоначальной настройке БД. Его редактирование через интерфейс не реализуется. Пример начальных категорий для демонстрации: «Организационные», «Документация», «Обслуживание», «Прочее». Это пример наполнения, а не утверждённый обязательный набор значений.

### Task

Поля:

- `id: int`;
- `title: str` — название;
- `description: str` — необязательное описание;
- `assignee_id: int` — ID ответственного пользователя;
- `category_id: int` — ID категории;
- `due_date: date` — срок выполнения, без времени;
- `priority: Priority` — фиксированный приоритет;
- `status: TaskStatus` — текущий статус.

Методы:

- `change_status(new_status)` — проверка предметного правила перехода;
- `is_overdue(current_date: date) -> bool` — вычисление просрочки.

Название, ответственный, категория, приоритет и срок обязательны. Статус при создании задаётся автоматически. Описание может быть пустым.

### Связи

```text
User     1 ─── 0..* Task     Один ответственный у каждой задачи
Category 1 ─── 0..* Task     Одна категория у каждой задачи
```

Один пользователь может иметь ноль или много задач. Каждая задача имеет ровно одного существующего ответственного и ровно одну существующую категорию.

Статусы и приоритеты являются фиксированными перечислениями в модели. В концептуальной схеме они могут быть показаны как отдельные понятия, но отдельные таблицы для их редактирования не нужны.

Отчёт — временный результат формирования текста по выбранным задачам. В БД нет таблицы отчётов. Постоянную сущность `Report`, историю отчётов и архив сформированных отчётов не создавать.

Наследование между `User`, `Task`, `Category` и сервисами не требуется. Связи в принятой диаграмме классов представлены ассоциациями и зависимостями. Не добавляй наследование или композицию ради оформления диаграммы.

## 6. Статусы, приоритеты и просрочка

Статусы в интерфейсе:

- «Новая»;
- «В работе»;
- «Выполнена».

Начальный статус каждой создаваемой задачи — **«Новая»**.

| Текущий статус | Разрешённые новые статусы |
|---|---|
| Новая | В работе |
| В работе | Новая, Выполнена |
| Выполнена | В работе |

Прямые переходы «Новая → Выполнена» и «Выполнена → Новая» запрещены. Проверка относится и к редактированию задачи администратором. Повторное сохранение того же статуса можно обработать как отсутствие изменения.

Храни правило в одном месте и используй его в форме, сервисе и тестах. Проверяй переход относительно актуального статуса в БД при сохранении, а не только значения, которое ранее показал интерфейс.

Приоритеты:

- «Низкий»;
- «Средний»;
- «Высокий».

Сортируй приоритеты по смысловому порядку, а не по алфавиту.

Просрочка вычисляется:

```text
due_date < current_date AND status != «Выполнена»
```

Задача со сроком сегодня ещё не просрочена. Выполненная задача не отображается просроченной, даже если срок уже прошёл.

«Просрочена» не является дополнительным статусом и не записывается вместо текущего статуса. Не храни независимый столбец `is_overdue`, который может устареть.

Используй единый источник текущей даты для отображения и отчётов. Техническое решение: календарная дата PostgreSQL `CURRENT_DATE` с согласованной часовой зоной серверной настройки. В модульных тестах передавай дату явно.

Дата вводится календарным полем. ТЗ не запрещает создавать задачу с уже прошедшим сроком: не добавляй такой запрет автоматически. Несуществующая дата отклоняется.

## 7. Архитектура приложения

Сохранить три основных блока из структурной схемы:

1. пользовательский интерфейс;
2. бизнес-логика;
3. подсистема хранения данных.

Для конкретной реализации предлагается **MVP** с тонкими представлениями PySide6. Это технический выбор этого промпта: в ТЗ были указаны MVP/MVC без окончательного выбора.

```text
Qt Widgets и модели таблиц
          |
       Presenter
          |
AuthService / UserService / TaskService / ReportService
          |
     Database и psycopg2
          |
      PostgreSQL
```

Предметные сущности и перечисления не должны зависеть от PySide6 и psycopg2.

- UI показывает данные, собирает ввод и сообщает о действиях.
- Presenter связывает UI с сервисами и текущей сессией.
- Сервисы проверяют права, данные и предметные правила, выполняют сценарии.
- Слой `Database` управляет соединениями, запросами и транзакциями.

SQL-запросы не размещай в обработчиках кнопок. Внешние зависимости передавай явно через конструкторы; отдельный фреймворк DI не нужен.

Соответствие модулям структурной схемы:

| Модуль схемы | Реализация |
|---|---|
| Аутентификация и разграничение доступа | AuthService, сессия, проверки прав сервисов |
| Управление пользователями | UserService |
| Управление задачами | TaskService |
| Поиск, фильтрация и сортировка | TaskService и подготовка запросов к БД |
| Формирование отчётов | ReportService |
| Экспорт CSV | ReportService с отдельным небольшим обработчиком CSV |

Не создавай отдельный сервис для каждой кнопки. Поиск и экспорт могут быть выделены во вспомогательные модули без изменения бизнес-модели.

## 8. Сервисы и соответствие диаграмме классов

Сохрани принятые названия: `AuthService`, `UserService`, `TaskService`, `ReportService`, `User`, `Task`, `Category`.

### AuthService

Хранит ссылку на `UserService`.

Основное действие: `authenticate(login, password)`.

Проверяет логин и bcrypt-хеш. Возвращает безопасное представление текущего пользователя либо понятный результат отказа. Не возвращай обычному пользовательскому интерфейсу пароль или хеш.

Сессия хранится только в памяти. При выходе из учётной записи очисти пользовательский контекст, данные таблиц и ранее сформированные отчёты.

### UserService

Доступ к БД через `Database` или провайдер соединений.

Действия:

- `get_users()`;
- `create_user(...)`;
- `update_user(user_id, login, role)`;
- `delete_user(user_id)`;
- `reset_password(user_id, password)`;
- внутреннее получение учётных данных для аутентификации.

Администратор создаёт пользователя с логином, начальным паролем и ролью. Также он редактирует логин и роль существующей записи. Самостоятельная регистрация не предусмотрена.

Редактирование пользователя:

1. проверить актуальные права администратора;
2. проверить непустой уникальный логин и допустимую роль;
3. сохранить изменения без смены ID, пароля и назначенных задач;
4. обновить списки и подписи ответственных;
5. при отмене оставить запись неизменной.

Сброс пароля остаётся отдельной операцией. Переименование учётной записи не создаёт нового пользователя. При изменении роли активная сессия должна получать актуальные права, как указано в разделе 4.

Предлагаемое техническое правило: не допускать удаления или понижения роли последнего администратора. Проверка и изменение должны быть атомарными даже при работе двух клиентов. Это защита от потери административного доступа, а не дополнительная роль системы.

Удаление пользователя:

1. проверить права администратора;
2. проверить отсутствие назначенных задач;
3. если задачи есть, отказать с предложением сначала переназначить их;
4. после переназначения всех задач разрешить повторное удаление.

Не удаляй задачи вместе с пользователем и не оставляй их без ответственного. Проверка и удаление выполняются с соблюдением транзакционной целостности и ограничений FK.

При сбросе администратор вводит новый временный пароль. Старый пароль перестаёт работать после успешного сохранения нового хеша. Принудительная смена пароля при следующем входе не описана в ТЗ и не требуется.

### TaskService

Доступ к БД через `Database` или провайдер соединений.

Действия:

- `get_tasks(user, query, filters, sort)`;
- `create_task(...)`;
- `update_task(...)`;
- `delete_task(task_id)`;
- `change_status(task_id, status, user)`;
- получение выбранных задач с повторной проверкой доступности.

Расширение `get_tasks` параметрами `query` и `sort` необходимо для обязательных поиска и сортировки. Эти действия не должны существовать только в виджетах.

Действующего пользователя для проверки прав получай из доверенного контекста текущей сессии. Не принимай роль непосредственно из пользовательской формы.

Назначение исполнителя обязательно при создании. При редактировании администратор может заменить его другим существующим пользователем. После обновления списков задача исчезает у прежнего исполнителя и появляется у нового.

Удаление задачи требует подтверждения. Отмена создания, редактирования или удаления оставляет БД неизменной.

### ReportService

Хранит ссылки на `TaskService` и `UserService`.

Действия по смыслу принятой диаграммы:

- `create_task_report(...)` — текст по одной задаче;
- `create_summary(...)` — текст по нескольким выбранным задачам;
- `export_tasks(...)` — CSV со списком задач;
- `export_users(...)` — CSV со списком пользователей.

Формирование отчёта повторно читает актуальные данные и проверяет права. Не доверяй списку готовых объектов, присланному интерфейсом, без проверки их ID и доступности.

Сигнатуры могут быть уточнены для сессии, ID и типизированных параметров. Отрази это в актуальной диаграмме классов. Сохраняй назначение сервисов и основные зависимости.

На уровне модели `Task.change_status` проверяет правило, а `TaskService.change_status` проверяет право пользователя и сохраняет изменение. Это разные обязанности.

## 9. PostgreSQL и постоянные данные

PostgreSQL — единый источник постоянных данных для всех клиентов. Локальные JSON, CSV и коллекции в памяти не заменяют основную БД. Локальный автономный режим с последующей синхронизацией не предусмотрен.

Основные таблицы:

### users

| Поле | Назначение |
|---|---|
| id | Первичный ключ |
| login | Непустой уникальный логин |
| password_hash | Непустой bcrypt-хеш |
| role | USER или ADMIN |

### categories

| Поле | Назначение |
|---|---|
| id | Первичный ключ |
| name | Непустое название категории |

### tasks

| Поле | Назначение |
|---|---|
| id | Первичный ключ |
| title | Непустое название |
| description | Необязательный текст |
| assignee_id | NOT NULL, FK на users.id |
| category_id | NOT NULL, FK на categories.id |
| due_date | NOT NULL, PostgreSQL DATE |
| priority | LOW, MEDIUM или HIGH |
| status | NEW, IN_PROGRESS или COMPLETED; по умолчанию NEW |

В коде используй перечисления и явное отображение на русские подписи интерфейса. В БД допустимо использовать текстовые коды с CHECK-ограничениями. Значения не должны расходиться между БД, моделью и интерфейсом.

Технические идентификаторы `assignee_id` и `category_id` реализуют структурные связи концептуальной модели. Таблица many-to-many для исполнителей не нужна.

Настроить:

- первичные ключи;
- внешние ключи и `NOT NULL` для обязательных связей;
- уникальность логина;
- CHECK для допустимых ролей, статусов и приоритетов;
- проверку непустого названия;
- индекс по `tasks.assignee_id`;
- необходимые индексы по результатам проверки запросов.

Удаление связанного пользователя или категории должно блокироваться ограничениями БД. Каскадное удаление задач вместе с ними запрещено.

Сценарии создания схемы и начального наполнения отдели от сценария загрузки демонстрационных задач. Не создавай тестовые записи при каждом запуске клиента.

Обновления схемы выполнять предоставляемыми SQL-сценариями. Клиент не должен автоматически пересоздавать существующие таблицы или терять данные.

## 10. Подключения, транзакции и многопользовательская работа

Предусмотреть настройки подключения: адрес сервера, порт, имя БД, технический пользователь PostgreSQL, пароль и тайм-аут.

Прикладные учётные записи в `users` и техническая учётная запись PostgreSQL — разные понятия. Логин исполнителя не должен автоматически считаться логином PostgreSQL.

Реальные параметры подключения и пароли не включать в исходный код или репозиторий. Предоставить пример конфигурации без секретов и способ настройки на рабочей станции. Не запускать обычный клиент с правами PostgreSQL superuser.

Использовать параметризованные SQL-запросы. Динамические имена полей сортировки выбирать только из разрешённого списка.

Соединения и курсоры корректно закрывать. Транзакция охватывает целую логическую операцию. При ошибке выполнять rollback.

Не разделяй один активный курсор или транзакцию между параллельными действиями разных потоков. Если используется фоновая работа, выдавай ей собственное соединение или организуй последовательный доступ.

Пример потока сохранения:

```text
Действие пользователя
    → Presenter
    → проверка прав и данных в сервисе
    → транзакция PostgreSQL
    → commit или rollback
    → результат операции
    → обновление интерфейса
```

Успешное сообщение показывай только после подтверждённого commit. Если связь потеряна в момент commit и исход неизвестен, сообщи об этом и перечитай данные после восстановления связи. Не повторяй автоматически изменяющий запрос с риском дублирования.

Два клиента используют одну БД. Кнопка «Обновить» перечитывает актуальный список. Мгновенные push-уведомления и сложная синхронизация не требуются.

При изменении статуса учитывай конкурентное изменение другим клиентом: перечитай или заблокируй актуальную запись внутри транзакции, проверь переход и лишь затем сохраняй. При удалённой или недоступной задаче покажи понятное сообщение и обнови список.

Не называй разграничение в клиентском сервисе защитой от произвольного прямого подключения к БД. Описывай фактические границы выбранной архитектуры без добавления отдельного сервера приложения.

## 11. Поиск, фильтрация и сортировка

Эти операции доступны обеим ролям в пределах их прав.

### Поиск

- Поиск по названию **или** описанию задачи.
- Полная или частичная подстрока.
- Без учёта регистра, включая кириллицу.
- Пустой запрос снимает текстовое условие поиска.
- Отсутствие совпадений показывает пустой результат с понятным сообщением.
- Символы `%`, `_` и кавычки трактуются как обычный пользовательский ввод, а не SQL-код или произвольные шаблоны.

### Фильтры

- статус;
- приоритет;
- категория;
- срок выполнения: выбранная дата или диапазон дат;
- для администратора — выбранный ответственный пользователь.

Совместно заданные фильтры соединяются условием **AND**. Текстовое условие по названию или описанию применяется к уже разрешённым задачам.

Отображай включённые фильтры и предоставь кнопку сброса. Сброс поиска или фильтров не меняет прикладные права.

### Сортировка

По названию, сроку выполнения, приоритету, статусу и категории. Последняя включена в требования к пользовательской сортировке в ТЗ, хотя не перечислена в предварительном тесте №6.

Поддержать прямое и обратное направления. Смысловой порядок:

```text
Приоритет: Низкий → Средний → Высокий
Статус:    Новая → В работе → Выполнена
```

Для одинаковых значений используй ID как дополнительный критерий устойчивого порядка.

Для объёма 1000 задач достаточно простых запросов. Не добавляй сложный поисковый движок без необходимости.

## 12. Интерфейс и переходы между окнами

Интерфейс на русском языке, с понятными действиями и доступными по роли кнопками. Используй стандартные виджеты, таблицы, формы и диалоги Qt Widgets. Формы должны корректно отображаться при изменении размера окна.

При запуске сразу показывается **окно авторизации**.

### Авторизация

- логин;
- пароль с маскировкой;
- «Войти»;
- возможность закрыть приложение.

Ошибка входа оставляет пользователя в окне авторизации и показывает сообщение. Главный интерфейс до успешного входа не открывается.

### Главное меню

- «Работа с задачами»;
- «Управление пользователями» — только ADMIN;
- «Отчёты и экспорт»;
- «Справка»;
- «Выйти из учётной записи»;
- «Завершить работу».

Показывать текущий логин и роль. Для обычного пользователя раздел отчётов доступен, а операции CSV скрыты или недоступны.

### Работа с задачами

- таблица доступных задач;
- поиск;
- фильтры;
- сортировка;
- «Обновить» и сброс условий;
- выбор одной или нескольких задач для отчёта;
- изменение статуса выбранной собственной задачи;
- административные действия создания, редактирования, удаления и назначения.

Колонки таблицы: название, ответственный, категория, приоритет, срок, статус и признак просрочки. Описание выбранной задачи показать в панели сведений на этом же экране. Имя ответственного получать по ID учётной записи: переименование пользователя не должно разрывать назначение.

Отдельная обязательная «карточка задачи» не вводится. Детальные сведения являются представлением уже существующей задачи, а не новой сущностью или самостоятельной функцией предметной области.

Визуально обозначать статусы и просрочку цветом и/или иконкой, сохраняя текстовую подпись. Цвет не должен быть единственным способом различить состояния.

### Форма создания и редактирования задачи

- название;
- описание;
- ответственный из списка;
- категория из БД;
- приоритет;
- срок через календарное поле;
- отображение текущего статуса при редактировании;
- сохранение и отмена.

Форма доступна администратору. При создании статус «Новая» задаётся автоматически. Если статус редактируется, предлагаются только разрешённые переходы; проверка также выполняется в сервисе.

### Управление пользователями

- список логинов и ролей;
- добавление пользователя;
- редактирование логина и роли выбранного пользователя;
- удаление пользователя;
- сброс пароля;
- переход к задачам выбранного пользователя.

Пароли и хеши не отображать. Создание и редактирование учётной записи, сброс пароля могут быть небольшими модальными диалогами. При редактировании пароль не изменяется; отмена не записывает новые значения.

### Отчёты и экспорт

- отображение выбранных задач;
- формирование текстового отчёта;
- просмотр текста с возможностью стандартного выделения и копирования;
- для ADMIN — экспорт списка задач и списка пользователей в CSV с выбором пути.

### Справка

Справка работает локально и описывает роли, вход, поиск, фильтры, статусы, отчёты, экспорт и основные сообщения об ошибках. Возврат закрывает справку и показывает предыдущий раздел.

### Завершение работы

Любая попытка закрыть приложение, включая крестик окна авторизации, должна открыть **«Подтверждение выхода»** с действиями «Выйти» и «Отмена».

- «Выйти» завершает приложение и освобождает ресурсы.
- «Отмена» сохраняет текущую сессию и возвращает ровно к тому окну, из которого пытались выйти.
- «Выйти из учётной записи» очищает сессию и возвращает к авторизации; приложение продолжает работать.
- Если открыта форма с несохранённым вводом, отмена закрытия сохраняет этот ввод. Завершение работы не должно случайно сохранить отменённые изменения.

Соответствие графу состояний:

```text
Запуск → Авторизация
Авторизация → успешный вход → Главное меню
Авторизация → ошибка входа → Авторизация
Главное меню ↔ Работа с задачами
Главное меню ↔ Управление пользователями [ADMIN]
Главное меню ↔ Отчёты и экспорт
Главное меню ↔ Справка
Главное меню → выход из учётной записи → Авторизация
Текущее окно → попытка закрытия → Подтверждение выхода
Подтверждение выхода → отмена → исходное окно
Подтверждение выхода → подтверждение → завершение программы
```

Не блокируй главный поток Qt длительными запросами, хешированием пароля, формированием файлов или повторным подключением. Обновление виджетов выполняй в GUI-потоке.

## 13. Отчёты

Обе роли могут формировать отчёт по одной или нескольким выбранным доступным задачам.

Обязательные сведения для каждой задачи:

- название;
- ответственный пользователь;
- приоритет;
- срок выполнения;
- категория;
- текущий статус;
- признак просрочки.

Отчёт строится по текущим данным PostgreSQL. Если выбранная задача уже удалена или перестала быть доступной, сообщи об изменении данных и предложи обновить выбор.

Без выбранных задач отчёт не формируется: показать «Выберите хотя бы одну задачу».

Текст отчёта хранится только как временный результат в памяти. При выходе из учётной записи он очищается. Создание отчёта не должно добавлять записи в БД.

Слово «отчёт о выполнении» означает отображение текущего состояния задач. Трудозатраты, фактическая дата завершения и история переходов в принятой модели не предусмотрены; не выдумывай эти сведения.

PDF, DOCX, печать, диаграммы аналитики и архив отчётов не входят в обязательный результат.

## 14. Экспорт в CSV

CSV доступен администратору.

Два вида экспорта:

1. список задач;
2. список пользователей.

Требования:

- UTF-8;
- разделитель `;`;
- первая строка — заголовки колонок;
- корректные кавычки, разделители, переносы строк, кириллица и пустые значения;
- выбранная пользователем папка и имя файла;
- понятное сообщение при отсутствии доступа к папке или ошибке записи;
- отмена выбора файла не создаёт файл;
- успех отображается только после завершения записи.

Поля задач: ID, название, описание, ответственный, категория, приоритет, срок и статус. Признак просрочки можно добавить как вычисляемую колонку.

Поля пользователей: ID, логин, роль.

Пароли и хеши не экспортируются. Эта защита должна действовать независимо от текущего набора колонок GUI. Используй явный разрешённый список полей.

Техническое правило объёма экспорта: экспорт задач соответствует текущему доступному списку после поиска, фильтрации и сортировки; экспорт пользователей содержит список учётных записей. Это правило явно описать в справке.

Не изменяй исходный текст при сериализации: кавычки и разделители должны корректно экранироваться средствами CSV.

## 15. Ошибки и восстановление

Предусмотреть понятные сообщения для:

- неверных данных входа;
- отсутствия полномочий;
- незаполненных обязательных полей;
- повторяющегося логина;
- несуществующего ответственного или категории;
- недопустимого перехода статуса;
- удаления пользователя с задачами;
- отсутствия результатов поиска;
- недоступной PostgreSQL или неверной конфигурации;
- потери связи при операции;
- ошибки сохранения или экспорта;
- изменения/удаления выбранной задачи другим клиентом.

При недоступности PostgreSQL программа не завершается аварийно, не показывает неуспешную операцию как выполненную и предоставляет действие «Повторить подключение».

После восстановления доступности сервера повторное подключение и продолжение работы должны занимать не более 1 минуты с момента команды пользователя. Настрой конечные тайм-ауты; бесконечное ожидание запрещено.

Если БД уже содержит сохранённые данные, сбой или обновление клиента не должен их удалять. Повторная установка клиента не пересоздаёт БД.

Пользователю показывай понятное описание, технические подробности записывай в локальный журнал. Пароли, хеши и строку подключения с секретами не логировать.

Не подавляй все исключения общим возвратом `True` или пустого списка. Отличай пустой результат от ошибки загрузки.

## 16. Резервное копирование и обновление

Резервное копирование и восстановление выполняются обслуживающим администратором стандартными средствами PostgreSQL по руководству системного программиста.

Документировать:

- создание резервной копии;
- восстановление в отдельную тестовую БД;
- проверку пользователей, категорий, задач и связей после восстановления;
- обновление клиента заменой `.exe`;
- применение SQL-сценария при изменении структуры БД.

Не создавай отдельный сложный интерфейс управления резервными копиями. Не выполняй разрушительное восстановление рабочей БД автоматически.

## 17. Демонстрационные данные

Отделить инициализацию рабочей системы от демонстрационного наполнения.

Для демонстрации подготовить:

- одну учётную запись администратора;
- несколько пользователей, включая пользователя без задач;
- начальные категории;
- задачи всех трёх статусов и приоритетов;
- задачи разных категорий и ответственных;
- просроченные невыполненные задачи;
- выполненные задачи с прошедшим сроком;
- задачи со сроком сегодня и в будущем;
- задачи с пустым описанием;
- названия и описания с кириллицей, кавычками и разделителями.

Все демонстрационные задачи должны удовлетворять обязательным связям. Пользователю без задач не назначать фиктивную задачу.

Первого администратора создавай отдельной процедурой настройки. Его пароль вводится при настройке и хешируется через bcrypt. Не задавай постоянный пароль для рабочей системы в исходниках.

Допустимы явно отмеченные демонстрационные учётные данные в инструкции для тестовой БД. Не загружать демонстрационные данные в рабочую БД без явной команды.

Для нагрузочных проверок отдельным генератором подготовить 100 пользователей и 1000 задач. Генератор не запускается обычным клиентом.

## 18. Требования к производительности

При объёме до 1000 задач:

| Показатель | Ограничение ТЗ |
|---|---|
| Отображение списка | Не более 2 секунд |
| Поиск | Не более 2 секунд |
| Фильтрация | Не более 2 секунд |
| Сортировка | Не более 2 секунд |
| Формирование отчёта | Не более 5 секунд |
| Экспорт CSV | Не более 5 секунд |
| Оперативная память клиента | Не более 300 МБ, без PostgreSQL |
| Размер БД при 100 пользователях и 1000 задачах | Не более 100 МБ, без резервных копий |

Измерять время от действия пользователя до готового результата, а не только выполнение SQL. Используй обычные демонстрационные текстовые данные; размер полей и условия нагрузки зафиксируй в протоколе.

Нагрузка должна проверяться на реальной PostgreSQL. Для памяти зафиксировать способ измерения и учесть фактически запущенные процессы упакованного клиента. Для объёма БД использовать измерение размера базы, а не только SQL-файла.

Результаты сопровождать сведениями об ОС, процессоре, памяти, версиях ПО и сетевых условиях. Не заявляй выполнение нормативов без измерений. Если среда недоступна, явно отметь, какие проверки ожидают выполнения на целевой машине.

Классы в UML оформлять тремя секциями: имя, поля, методы; использовать типы, видимость, корректные связи и кратности. Не рисуй наследование между независимыми предметными сущностями. При изменении сигнатур или структуры обновляй материалы РПЗ.

Схема логической декомпозиции не является обязательной. Старые повторы авторизации и управления задачами и «все задачи» для обычного пользователя не являются дополнительными требованиями. Редактирование логина и роли включено на основании отдельного нового указания пользователя; соответствующие схемы обновить.

Формы интерфейса для РПЗ получать из готовой программы: не требуется заранее создавать отдельный комплект выдуманных макетов.

## 22. Технические уточнения этого промпта

Следующие решения конкретизируют ранее неполные детали. Они должны быть записаны в `docs/implementation_decisions.md`; не объявляй их дословными пунктами утверждённого ТЗ.

1. **MVP.** Предлагается для связи Qt Widgets и сервисов; окончательный шаблон не был зафиксирован в ТЗ.
2. **Идентификаторы связей.** `assignee_id` и `category_id` реализуют отношения модели; это технические поля, а не новые функции.
3. **Соединения.** Обёртка `Database` или провайдер вместо одной общей активной connection позволяет корректно выполнять фоновые операции. При необходимости уточняется тип атрибута в диаграмме сервисов.
4. **Статус у администратора.** Меняется в рамках редактирования по тем же переходам. Не вводится специальная возможность обходить правила.
5. **Порядок сортировки.** Приоритеты и статусы имеют смысловой порядок; для одинаковых значений используется ID.
6. **Фильтр срока.** Диапазон включает обе границы. Некорректный диапазон с началом после конца отклоняется.
7. **Дата просрочки.** Используется согласованная календарная дата сервера PostgreSQL; единый подход документируется.
8. **Объём экспорта.** CSV задач соответствует текущему отобранному списку. CSV пользователей экспортирует безопасные поля списка пользователей.
9. **Логины.** Для первоначальной реализации предлагается сравнение без учёта регистра с удалением внешних пробелов. Одинаковое правило применяется при создании и входе и обеспечивается уникальным ограничением/индексом БД. Пароли регистрозависимы и не нормализуются.
10. **Сведения о задаче.** Показываются в панели рабочего раздела; отдельная карточка не вводится.
11. **Категории.** Названия начальных демонстрационных категорий являются наполнением, а не неизменяемыми требованиями предметной области.
12. **Ограничения длины.** ТЗ не задаёт произвольных максимумов длины полей. Не придумывай такие бизнес-ограничения. Технические ограничения bcrypt и виджетов проверяй по используемым версиям и сообщай о них ясно, без молчаливого усечения.
13. **Последний администратор.** Предлагается блокировать его удаление и смену роли на USER, чтобы сохранить возможность обслуживания системы. Правило выполняется в транзакции с защитой от конкурентного изменения.
14. **Активные сессии.** Изменение роли учитывается сервисами по текущей записи в БД. Переименование сохраняет ID сессии и назначения; удаление учётной записи прекращает её доступ при следующем защищённом запросе.

Если принятое уточнение конфликтует с более новым указанием пользователя, используй новое указание и обнови описание решения и тесты.

## 25. Критерий готовности

Проект готов, когда:

1. Вход обеими ролями работает с настоящей PostgreSQL.
2. Обычный пользователь получает только свои задачи и разрешённые действия.
3. Администратор управляет задачами и пользователями, редактирует логин и роль, назначает и меняет ответственного. Изменённая роль применяется и к уже открытой сессии.
4. Все задачи имеют обязательные поля, одну категорию и одного ответственного.
5. Поиск, фильтрация и сортировка работают совместно и сохраняют ограничения доступа.
