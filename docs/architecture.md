# Архитектура и основные классы

Использован MVP: Qt Widgets → Presenter → сервисы → Database → PostgreSQL. Выбор соответствует техническому уточнению MasterPrompt, а не объявляется отдельным ранее согласованным решением ТЗ.

| Модуль | Ответственность |
|---|---|
| `domain.py` | User, Category, Task, Session, TaskInput, TaskQuery, перечисления и предметные правила; без Qt/psycopg2 |
| `config.py` | Чтение и запись внешнего INI, проверка тайм-аутов, пути конфигурации и журнала |
| `database.py` | Соединение на операцию, курсор, commit/rollback, перевод ошибок PostgreSQL |
| `services.py` | AuthService, UserService, TaskService, ReportService, безопасная сериализация CSV |
| `ui/views.py` | Формы, таблицы, навигация; без SQL |
| `ui/table_models.py` | Отображение строк Qt, цвета и текст просрочки |
| `ui/presenter.py` | Сессия, связывание действий формы с сервисами, обновление роли и данных |
| `ui/workers.py` | QRunnable + сигналы Qt, выполнение операций вне GUI-потока |
| `bootstrap.py` | Создание приложения, журналирование, зависимости, запуск |

Малые модули модели и сервисов объединены, чтобы не дробить курсовой проект на десятки однотипных файлов. Зависимости передаются через конструкторы, отдельного DI-фреймворка нет.

## Сценарий сохранения

1. Представление собирает данные в `TaskInput`.
2. Presenter запускает Worker; GUI остаётся отзывчивым, повторный запуск операции временно недоступен.
3. Сервис проверяет данные и читает текущие полномочия пользователя из БД по `Session.user_id`.
4. Database открывает отдельную транзакцию. Сервис блокирует изменяемую задачу, проверяет переход относительно её текущего состояния и записывает данные.
5. Только после commit результат поступает через Qt-сигнал. Presenter обновляет список в GUI-потоке.

Сервисная функция, возвращающая результат внутри `with transaction()`, фактически отдаёт его вызывающему коду после выхода из контекстного менеджера и успешного commit. Ошибка commit превращается в ошибку операции.

## Роль и сеанс

В Session хранится только ID. Каждый защищённый метод вызывает `current_user`. Presenter дополнительно проверяет пользователя до и после операции. При изменении роли данные прежнего уровня доступа очищаются; результат, полученный при смене роли, не отображается. Переименование не меняет ID; удаление учётной записи вызывает SessionExpired и возврат к входу.

Это проверка штатных клиентских сценариев. Техническая роль PostgreSQL общая; SQL-доступ с её паролем не изолирован по прикладным логинам.

## Конкурентность

- Статусы: `SELECT ... FOR UPDATE OF t`, затем правило перехода и UPDATE в одной транзакции.
- Последний администратор: `pg_advisory_xact_lock` сериализует операции с пользователями. Проверка количества администраторов и понижение/удаление атомарны относительно других клиентов приложения.
- Удаление исполнителя: проверка задач и FK RESTRICT; задача не может остаться без исполнителя.
- Остальные поля задачи: последнее успешное сохранение. История и отдельная версия строки не добавлены.
- Несколько потоков не делят соединения; в одном клиенте фоновые действия идут последовательно.

## Ошибки и файлы

AppError предназначен для понятного пользователю текста. DatabaseError сообщает о доступности, тайм-ауте или неизвестном исходе commit. Технический журнал содержит тип, SQLSTATE и этап ошибки, а не SQL-параметры и секреты. Неожиданные ошибки записываются по типу и позициям вызовов без значений локальных переменных.

CSV сначала полностью записывается в временный файл в выбранной папке, затем заменяет конечный файл. Исключения не превращаются в пустой список или успешный результат. Запросы записи автоматически не повторяются.
